# Разбор: платежи, полосы, outbox, webhook (2026-06-10)

Итерация написана Claude автономно (ты делегировал «закончить весь бэкенд»). Этот разбор —
для твоего ревью: почему сделано так, где компромиссы, что проверить руками. Аналогии с
.NET/EF — в скобках.

## 1. Платежи (`Payment`, схема v10)

**Решения и почему:**
- **Отдельная таблица, не поля на грузе.** Бизнес мультиканальный: один груз закрывается
  несколькими платежами разными способами (часть безналом, часть наличными). Поля на грузе
  не выразили бы N платежей. (EF-аналогия: коллекция-навигация `Shipment.Payments`.)
- **`amount` — `decimal.Decimal`, не `NullDecimal`:** сумма обязательна, в отличие от
  weight/volume груза. CHECK `amount > 0` в БД дублирует проверку сервиса — defense in depth.
- **Валюта платежа ≠ валюта груза.** Груз может стоить в USD, а платёж прийти в RUB.
  Дефолт — валюта груза, но поле своё.
- **`created_by` nullable + `ON DELETE SET NULL`:** платёж — финансовый факт, он переживает
  удаление менеджера (как `changed_by` в истории статусов).
- **`shipment_id` — `ON DELETE RESTRICT`:** груз с деньгами удалить нельзя. Сравни с
  `shipment_status_events` (CASCADE — история без груза не нужна). Это сознательная
  асимметрия: история — производная, деньги — нет.
- **Гонка «груз удалили между проверкой и INSERT»:** сервис проверяет `GetByID`, но истину
  держит FK. Репозиторий транслирует `23503` по имени констрейнта в `domain.ErrNotFound` —
  тот же приём, что 23505 в `ClientRepository` (паттерн A1a).
- **`UPDATE ... RETURNING` для смены статуса** — как `LeadRepository.UpdateStatus` (A1c):
  одна строка — транзакция не нужна, RETURNING убирает гонку read-after-write.

**Проверь руками:** `POST /api/shipments/{id}/payments` с `{"amount": "100.50", "channel":
"cash"}` (decimal принимает и строку, и число — строка надёжнее для копеек).

## 2. Полоса (`lane`, схема v11)

Ратифицировал ты: метка на грузе, не три потока. `varchar(10) + CHECK`, дефолт `cargo`
(существующие строки легально становятся карго — исторически так и было). Go-сторона —
типизированная строка с `IsValid()`, как `ShipmentStatus`. Lane задаётся при создании и
пока не меняется ручкой — если менеджерам понадобится перевод груза между полосами, это
отдельное решение (там появятся вопросы перерасчёта цены).

## 3. Доверенные прокси (техдолг #20)

Gin по умолчанию верит `X-Forwarded-For` от кого угодно → лимитер обходился подделкой
заголовка. Теперь `SetTrustedProxies`: дефолт — приватные диапазоны + CGNAT `100.64.0.0/10`
(на Railway до контейнера дотягивается только платформенный LB; публичный клиент не может
прийти с приватного адреса), override — `TRUSTED_PROXIES`. Битый CIDR валит процесс на
старте: `NewRouter` теперь возвращает `(engine, error)` — ошибка конфигурации должна
останавливать деплой, а не молча деградировать (тот же принцип, что `config.Validate`).

## 4. Outbox уведомлений (схема v12, закрывает #11/#15)

**Проблема:** уведомления слались fire-and-forget; рестарт процесса или icмык Telegram
терял сообщение навсегда.

**Решение:** `Notify*` теперь пишут готовый текст в таблицу `notifications`; горутина
`RunOutbox` каждые 3с забирает due-записи и шлёт, при ошибке — ретрай с экспоненциальным
backoff (30s → 30m, 10 попыток → терминальный `failed`).

**Ключевые места для ревью:**
- **Сервисы не изменились вообще.** Они зовут те же интерфейсы (`Notifier`, `ClientNotifier`…),
  outbox подключён внутри бота (`UseOutbox`). Это сила consumer-side интерфейсов: реализацию
  подменили, контракт цел. (.NET-аналогия: декоратор поверх `INotifier` в DI.)
- **Текст рендерится при постановке,** а не при отправке: диспетчер не зависит от доменных
  связей; минус — правка формата не затронет уже поставленные сообщения. Осознанный размен.
- **At-least-once:** упади процесс между `send` и `MarkSent` — на старте уйдёт дубль. Дубль
  приемлемее потери. Пометки идут через `context.WithoutCancel`, чтобы штатный shutdown не
  отменял запись о уже отправленном (см. коммит-фикс).
- **Частичный индекс** `WHERE status = 'pending'` — очередь обычно почти пуста, индекс
  не растёт вместе с архивом отправленных.
- **Ограничение (техдолг #21):** один диспетчер на процесс, `Due` без `SKIP LOCKED`. Два
  инстанса API начнут дублировать. Сегодня инстанс один; масштабирование — повод для claim.

## 5. Webhook-режим бота (env-gated)

- `TELEGRAM_WEBHOOK_URL` + `TELEGRAM_WEBHOOK_SECRET` заданы → на старте `setWebhook`
  (через `MakeRequest`: библиотека v5.5.1 не знает `secret_token` из Bot API 6.0), апдейты
  приходят на `POST /api/telegram/webhook`. Не заданы → прежний long polling, который теперь
  сам снимает webhook (`deleteWebhook`) — иначе `getUpdates` ловит 409. Переключение в обе
  стороны безопасно.
- **Аутентификация ручки:** Telegram возвращает секрет в заголовке каждого запроса;
  сравнение `subtle.ConstantTimeCompare` (не `==` — тайминг-атаки на подбор). Тело
  ограничено 1MB.
- **Слои не перемешаны:** HTTP-хендлер передаёт боту сырые байты (`ProcessUpdateJSON`),
  пакет `handlers` не импортирует tgbotapi.
- **Наполовину заданная конфигурация** (URL без секрета, http вместо https) валит процесс
  в ЛЮБОМ окружении, включая dev — это ошибка оператора, не режим работы.
- **На Railway пока не включён** (техдолг #22): достаточно задать обе переменные и redeploy.
