# Технический долг и MVP-решения

Реестр решений, принятых ради скорости MVP. Каждое сознательно упрощено — здесь
записано, **почему так сейчас**, **когда менять** и **на что**. Не удалять строку,
пока долг не закрыт; при закрытии — перенести в раздел «Закрыто» с датой.

Конвенция в коде: на месте упрощения ставим `// NOTE: MVP — <что>; см. docs/tech-debt.md`.

## Открытые

### 1. JWT в заголовке `Authorization: Bearer`
- **Сейчас:** access-токен хранится фронтом и шлётся в заголовке.
- **Почему:** проще всего для SPA + API, стандартный поток, понятно для обучения.
- **Риск:** токен доступен JS → уязвим к XSS.
- **Менять когда:** появится реальная админка с чувствительными действиями.
- **На что:** httpOnly+Secure cookie + CSRF-защита.

### 2. Без refresh-токена
- **Сейчас:** один access-токен с TTL в несколько часов, по истечении — релогин.
- **Почему:** refresh — это хранилище, ротация, отзыв; много кода ради малого на старте.
- **Менять когда:** менеджерам станет больно перелогиниваться.
- **На что:** пара access (короткий) + refresh (длинный, в БД, с отзывом и ротацией).

### 3. Создание менеджера через CLI
- **Сейчас:** `cmd/createmanager` заводит менеджера руками.
- **Почему:** одна компания, менеджеров единицы; публичной регистрации не нужно.
- **Менять когда:** менеджеры должны заводить менеджеров сами.
- **На что:** защищённая ручка «менеджер создаёт менеджера» поверх существующего CLI.

### 4. Смена статуса лида без стейт-машины
- **Сейчас:** `PATCH /leads/:id` принимает любой статус из enum, переходы не ограничены.
- **Почему:** менеджеру доверяем, в реальных воронках бывают исключения (вернуть из `rejected`).
- **Менять когда:** бизнес-правила переходов станут жёсткими.
- **На что:** явная стейт-машина допустимых переходов.

### 5. CORS `Access-Control-Allow-Origin: *` → закрыто 2026-06-09 (см. Закрыто)

### 6. Калькулятор: формула цены захардкожена на фронте
- **Сейчас:** лендинг считает диапазон цены по константам в JS.
- **Почему:** на MVP важен сам факт «показать вилку и собрать лид», не точность.
- **Менять когда:** появится реальная тарифная логика.
- **На что:** бэкенд-эндпоинт `POST /calc` с тарифами в БД/конфиге.

### 7. Бот: long polling
- **Сейчас:** `go-telegram-bot-api` на long polling.
- **Почему:** работает локально без публичного URL и TLS.
- **Менять когда:** деплой.
- **На что:** webhook.

### 8. Уведомления в единый чат (`MANAGER_CHAT_ID`)
- **Сейчас:** новый лид уведомляет один чат/группу из env.
- **Почему:** пер-менеджерская маршрутизация требует связи manager↔telegram_id, которой ещё нет.
- **Менять когда:** менеджеры авторизуются и привязывают свой Telegram.
- **На что:** рассылка по `telegram_id` из таблицы managers.

### 9. Gin в debug-режиме → закрыто 2026-06-09 (см. Закрыто)

### 10. Dev-дефолт `JWT_SECRET` → закрыто 2026-06-09 (см. Закрыто)

### 11. Уведомление о лиде — fire-and-forget в горутине → закрыто 2026-06-10
- **Закрыто 2026-06-09 (частично):** `service.Background` — дренаж фоновых отправок при
  остановке процесса.
- **Закрыто 2026-06-10 (полностью):** outbox — `Notify*` пишут отрендеренное сообщение в
  таблицу `notifications` (схема v12), диспетчер `bot.RunOutbox` шлёт с экспоненциальным
  backoff (30s→30m, 10 попыток → терминальный `failed`). Сбой Telegram или рестарт процесса
  уведомление не теряет; семантика at-least-once (редкий дубль приемлемее потери).

### 12. Отправка в Telegram без таймаута/отмены
- **Сейчас:** `bot.NotifyNewLead` игнорирует `ctx` — библиотека v5 не context-aware.
- **Почему:** простота на MVP.
- **Риск:** зависший запрос блокирует горутину.
- **Менять когда:** заметная доля отправок виснет.
- **На что:** HTTP-клиент с таймаутом / обёртка с `select` по `ctx.Done()`.

### 13. Миграция 000006: индекс в одной миграции с колонкой
- **Сейчас:** `add column lead_id` и `create index` в одном файле.
- **Почему:** одна маленькая аддитивная правка, миграция уже применена (v6), а менять
  применённую миграцию нельзя.
- **Расходится с:** `database.md` («индексы — отдельной миграцией для независимого отката»).
- **Менять когда:** при следующем индексе — выносить отдельно; 000006 не трогаем.

### 14. Кардинальность client.lead_id не зафиксирована → решено 1:1 (см. Закрыто)

### 15. Уведомления о статусе и сообщениях — fire-and-forget → закрыто 2026-06-10
- **Закрыто:** общий outbox — см. #11 (все четыре вида уведомлений идут через него).

### 20. Rate-limit берёт IP из `c.ClientIP()` (доверяет X-Forwarded-For) → закрыто 2026-06-10
- **Закрыто:** `NewRouter` вызывает `SetTrustedProxies`: дефолт — приватные диапазоны + CGNAT
  (до контейнера на Railway/в докере дотягивается только платформенный LB), override через
  `TRUSTED_PROXIES` (список IP/CIDR через запятую). Битое значение валит процесс на старте.

### 21. Outbox-диспетчер — один на процесс, без блокировок выборки
- **Сейчас:** `Due` без `FOR UPDATE SKIP LOCKED`; корректно при одном инстансе API.
  Дубли возможны в окно перекрытия инстансов при деплое (старый дренируется, новый уже
  поллит) и при горизонтальном масштабировании — приемлемо в рамках at-least-once.
- **Менять когда:** дубли при деплоях станут заметны или появится второй инстанс.
- **На что:** claim через `UPDATE ... SKIP LOCKED` либо вынести диспетчер в отдельный воркер.

### 23. Manager-JWT панели — в sessionStorage (XSS-доступен)
- **Сейчас:** панель менеджера хранит JWT в sessionStorage: переживает перезагрузку
  вкладки, но любой XSS на домене может его украсть.
- **Почему:** httpOnly-cookie требует перестройки auth на бэкенде (cookie+CSRF вместо
  Bearer); на MVP поверхность мала (нет пользовательского контента на домене панели).
- **Менять когда:** реальные клиенты и деньги в системе.
- **На что:** httpOnly secure cookie + SameSite + CSRF-токен, отдельный issue.

### 22. Webhook-режим не включён на Railway (код готов, env не заданы)
- **Сейчас:** бот на long polling; `TELEGRAM_WEBHOOK_URL`/`TELEGRAM_WEBHOOK_SECRET` не заданы.
- **Менять когда:** в любой момент — задать обе переменные в Railway (URL =
  `https://<railway-домен>/api/telegram/webhook`, секрет — случайная строка) и redeploy;
  откат — убрать переменные (поллинг сам снимает webhook).

### 16. Чат менеджера — только через API, без маршрутизации из Telegram
- **Сейчас:** клиент пишет в WebApp; менеджер отвечает ручкой `POST /shipments/:id/messages`
  (под JWT). Уведомление о сообщении клиента идёт в общий `MANAGER_CHAT_ID`, но ответить из
  этого чата нельзя — нет привязки сообщения Telegram ↔ груз.
- **Почему:** менеджерского UI в MVP нет, а reply-threading из группы — отдельная работа.
- **Менять когда:** появится менеджерская панель или потребуется отвечать прямо из Telegram.
- **На что:** менеджерский экран чата (поверх существующих ручек) или force-reply-маршрутизация.

### 17. Чат в WebApp без реального времени
- **Сейчас:** лента сообщений грузится при открытии экрана; новые ответы видны только при
  повторном входе (поллинга/SSE/WS нет).
- **Почему:** на MVP важен сам факт переписки, не мгновенность.
- **Менять когда:** переписка станет активным каналом.
- **На что:** поллинг с интервалом или SSE/WebSocket.

### 18. WebApp: client-JWT только в памяти, dev-обход `?token`
- **Сейчас:** токен клиента (`lib/api.ts`) хранится в памяти модуля — перезагрузка страницы
  означает повторную Telegram-авторизацию (внутри Telegram это бесплатно и незаметно). В
  DEV-сборке принимается `?token=` для локального прогона UI без Telegram.
- **Почему:** не храним токен в localStorage (XSS-поверхность); dev-обход удобен для отладки.
- **Риск:** `?token` обхода в проде нет — он за `import.meta.env.DEV`; убедиться, что так и
  останется при изменениях бутстрапа.
- **Менять когда:** появится потребность переживать перезагрузку вне Telegram.
- **На что:** при необходимости — короткоживущий токен + тихий refresh.

### 19. tracking_key: пред-проверка уникальности, без retry на конфликт вставки
- **Сейчас:** ключ (10 симв. Crockford base32 ≈ 50 бит) проверяется на существование перед
  вставкой; гарантия — unique-индекс в БД. Retry именно на 23505 при `INSERT` не делаем.
- **Почему:** вероятность коллизии при таком объёме энтропии ничтожна; пред-проверка
  избавляет от 500 в обычном случае.
- **Менять когда:** при огромных объёмах грузов.
- **На что:** retry на duplicate-key прямо вокруг `store.Create`.

### 26. JWT без отзыва: украденный токен живёт весь TTL (аудит 2026-06-11, major)
- **Сейчас:** нет logout, нет jti/blacklist. Дефолт TTL сокращён 24h → **4h** (2026-06-11),
  что сужает окно, но не закрывает проблему: XSS на панели (#23) всё ещё даёт часы доступа.
- **Стратегически:** jti в claims + хранилище активных токенов, logout-ручка, refresh для клиента.

### 27. TrustedProxies на проде — весь RFC1918+CGNAT (уточнение #20) → частично, 2026-06-11
- **Сейчас:** дефолт прежний (на одноузловом Railway безопасен), но вне dev при незаданном
  `TRUSTED_PROXIES` старт пишет warning в лог.
- **Остаток:** задать на Railway `TRUSTED_PROXIES` = адрес/подсеть их балансировщика (Hiki).

### 28. Мелкие security-находки аудита 2026-06-11 (пакетом)
- `initDataMaxAge` 24h → сократить до 15–30 мин (`internal/service/client.go`).
- Нет лимита длины текста: lead comment/cargo_type, chat text (→ лимиты в validate + CHECK).
- `Payment.UpdateStatus` не пишет, кто сменил статус (нет `updated_by` — разрыв аудит-следа).
- Общий `JWT_SECRET` на роли manager/client → два секрета.
- Webhook-ручка без rate-limit (секрет проверяется уже внутри хендлера).
- `err.Error()` с пользовательским вводом в 400-ответах → фиксированные сообщения.
- Контакты закрыты 2026-06-11: везде реальный @hikill8, фейковые телефон/почта убраны.
- Плейсхолдерные ИНН/ОГРН скрыты 2026-07-14; реальные реквизиты публикуются только после
  регистрации юридического лица и проверки документов.
- PDF-блобы в git-истории (`2b7022a`) — `git filter-repo` + force push, решение за Hiki.

## Закрыто

### 24. Лимит тела запроса (2026-06-11)
`middleware.MaxBodyBytes(64<<10)` на всю группу `/api` (`http.MaxBytesReader`): любой
легитимный JSON (формы, login, Telegram-апдейт) много меньше 64 КиБ, многомегабайтные
тела отбрасываются с 400. Внутренний 1 МиБ-лимит webhook-хендлера остался вторым рубежом.

### 25. Пагинация List-ручек (2026-06-11)
Лиды/клиенты/грузы/грузы-клиента: `?limit=&offset=` (дефолт 100, потолок 200), нормализация
в `service.Page.normalize` — границы действуют для любого вызывающего. Дочерние списки груза
(сообщения, платежи) — жёсткий `Limit(500)` в репо без параметров (offset-пагинация чату
не нужна, объём на груз мал). Бот `/status` — фикс. 50 свежих.

### 5. CORS — белый список origin'ов (2026-06-09)
`internal/http/router.go` `corsMiddleware` теперь отдаёт `Access-Control-Allow-Origin`, только
если `Origin` запроса в белом списке (`config.AllowedOrigins` ← env `ALLOWED_ORIGINS`). Вне
`development` пустой список => запрещены все источники (deny by default). В `development` без
явного списка для удобства отдаётся `*` (`AllowAnyOrigin`).

### 9. Gin `ReleaseMode` (2026-06-09)
`NewRouter` вызывает `gin.SetMode(gin.ReleaseMode)` при `AppEnv != development` (передаётся как
`RouterDeps.ReleaseMode`) до `gin.New()`.

### 10. Обязательный `JWT_SECRET` вне dev (2026-06-09)
`config.Validate()` (вызывается из `cmd/api/main.go` сразу после `Load`) падает с `os.Exit(1)`,
если вне `development` `JWT_SECRET` пуст/равен dev-дефолту, `DATABASE_URL` пуст/дефолтный или с
`sslmode=disable`, либо не заданы `TELEGRAM_BOT_TOKEN`/`MANAGER_CHAT_ID`. Ошибки собираются разом
(`errors.Join`).

### 14. Кардинальность client.lead_id — зафиксирована 1:1 (2026-06-04)
Миграция `000007` добавила partial unique index `uq_clients_lead_id ... where lead_id is not
null`: один лид → не более одного клиента. NULL (клиент пришёл не через форму) не конфликтуют.
